# RFC - Verify-gate Windows portability + fat-harness over-rejection

> Status: Implemented with monotonic verification.
> Scope: real Bash resolution, sanitized execution, and explicit unavailable
> verification that never fails or retries completed worker work.

## Problem

Two related failures observed in `ooo run`:

1. **Windows portability.** `_run_ac_verify_gate`
   (`src/ouroboros/orchestrator/parallel_executor.py:9843`) runs an AC's
   `verify_command` via `asyncio.create_subprocess_shell(command, cwd=cwd, ...)`.
   `command` strings are generated by seed-architect and assume bash idioms
   (`grep`, `&&`, POSIX paths, single quotes). Python's
   `create_subprocess_shell` defaults to `cmd.exe` on native Windows, which
   does not understand that syntax. Any AC verified via `verify_command` is at
   risk of breaking outright on Windows.

2. **Fat-harness over-rejection.** ACs without a `verify_command` fall back to
   transcript-backed evidence checking
   (`_verify_atomic_evidence_against_runtime_messages`,
   `src/ouroboros/orchestrator/evidence/verification.py:23-64`). If
   `support_messages` is empty, the AC is rejected outright with
   `"no runtime transcript evidence supports the typed evidence claims"`.
   Observed incident: an AC did 19m34s of real work (tests, edits) and was
   still rejected because the transcript evidence didn't reach the verifier
   (compaction or collection-timing suspected, not confirmed). Auto-retry then
   re-ran the whole AC, burning another ~20 minutes.

   Root cause is *not* the `job_observer` contract
   (`src/ouroboros/mcp/tools/job_observer.py`) — that's a read-only polling
   handoff for the host session to watch background jobs, unrelated to a
   leaf worker's own tool-call transcript. The actual fork is
   `verify_command` presence: when set, `_run_ac_verify_gate` runs the
   orchestrator's own command and the rest of evidence-checking is exempted
   (`_fat_harness_acceptance_error`, `parallel_executor.py:12836-12869`).
   Only ACs *without* `verify_command` take the fragile transcript path.

## Comparative research: gajae-code (GJC)

GJC's receipt system (`harness-control-plane/receipts.ts`) is a sha256-sealed
structured JSON envelope — conceptually more tamper-evident than
transcript-message matching. But its validation-command execution
(`finalize.ts:315`, test-adjacent code) hardcodes
`Bun.spawnSync(["bash", "-lc", spec.command], ...)`.

The actual Windows answer lives elsewhere: `packages/utils/src/shell-config.ts`
`getShellConfig()` resolves a **real POSIX-compatible shell binary** before
every shell command — priority: user-specified `shellPath` -> Git Bash
(`%ProgramFiles%\Git\bin\bash.exe`, x86 variant too) -> `bash.exe` on PATH
(Cygwin/MSYS2/WSL) -> explicit failure with an actionable install message. GJC
does not translate bash syntax per OS; it guarantees a real bash exists (or
fails loudly) so command authors only ever write POSIX syntax.

## Decision

### Part A — Windows-safe verify_command execution

Adopt GJC's "resolve a real shell, don't translate the command" pattern, with
one addition demanded by the owner (below): an LLM-advisory fallback instead
of a hard stop when no shell can be resolved deterministically.

**Invariant that must never break:** `_run_ac_verify_gate` exists so a
worker's self-report cannot be gamed. Whatever resolves *where* to run
`verify_command`, the actual pass/fail must still come from a deterministic
exit code of running that exact command (or an unmodified/pinned translation
of it) — never from an LLM's opinion that the AC "looks done".

**Tiered resolution** (owner-approved, supersedes the earlier "hard fail on
missing bash" draft):

- **Tier 0 (deterministic, free).** New `src/ouroboros/orchestrator/verify_shell.py`
  helper, `resolve_verify_shell()`, following the existing
  env -> config -> PATH priority used by `get_goose_cli_path()` /
  `get_pi_cli_path()`. POSIX: `/bin/bash` then `shutil.which("bash")`.
  Windows: `%ProgramFiles%\Git\bin\bash.exe` -> x86 variant ->
  `shutil.which("bash.exe")` (Cygwin/MSYS2/WSL). An `OUROBOROS_VERIFY_BASH`
  env override takes priority, and — per this repo's `.env` trust-boundary
  rule (`untrusted_env.py` denylist for `*_CLI_PATH`-style vars) — must be
  added to that denylist since it is an executable-path variable.
- **Tier 1 (LLM advisory, scoped to route selection only).** When Tier 0
  finds nothing, an LLM call receives *only* environment facts (candidate
  shell paths found/not-found, OS, available interpreters) and picks/builds
  an `ExecutionRoute` from that fixed candidate set. It never sees the AC,
  worker output, or verify_command semantics beyond the literal string. The
  orchestrator probes the chosen route with a harmless command
  (`echo ok && test -d .`) before trusting it. `verify_command` text is not
  modified in this tier.
- **Tier 2 (LLM translation, sealed second line).** Only when no POSIX
  interpreter exists at all: LLM translates `verify_command` to a
  PowerShell/cmd equivalent. To block the "rewrite to an easy command"
  failure mode, translation happens once during a pre-execution preflight,
  is pinned into the cache, and is **never re-translated after a failure** —
  there is no opportunity to loosen the command in response to a failing
  result.
- **Terminal case — quarantine, not silent pass.** If Tier 1/2 still can't
  produce a working route, the AC is marked `environment_unverifiable`. The
  run does not stop (per owner: "fail 처리로 멈추지마"), but the AC is never
  counted as a verified pass — it's surfaced in the final report as
  "unverifiable on this machine, needs manual confirmation." This is the only
  way to satisfy both "don't dead-end" and "don't fake a pass."

**Caching (cost/latency control).** Two caches, both keyed to avoid per-AC or
per-retry LLM calls on the common path:

- Machine cache (`~/.ouroboros/verify_route.json`), keyed by a machine
  fingerprint (OS + hash of which candidate paths exist). Same fingerprint =
  zero LLM calls.
- Translation cache, keyed by `sha256(verify_command) + machine fingerprint`.
  Retries and re-runs are cache hits.
- Resolution runs once per `ooo run` in a batch preflight over all ACs' verify
  commands, not lazily per AC — zero added latency on the steady-state path
  where Tier 0 succeeds.

**`_run_ac_verify_gate` changes:** replace `create_subprocess_shell(command)`
with `create_subprocess_exec(*resolved_route.argv)` (POSIX: effectively
`bash -c command`, unchanged semantics from today). `VerifyShellUnavailableError`
is demoted from a terminal failure to an internal signal that enters the
advisory tier, not a dead end.

### Part B — Reduce fat-harness's blast radius

1. **Push ACs toward `verify_command` by default.** Extend the existing seed
   preflight gate (memory: deterministic-executability check before RUN) with
   a new blocker, e.g. `ac_missing_verify_command`, for ACs that declare
   neither `verify_command` nor an explicit exemption reason
   (`AcceptanceCriterionSpec.verify_exemption_reason`, new field). Update
   seed-architect's prompt to prefer `verify_command` and require a reason
   when it's not feasible. `_run_ac_verify_gate` is immune to both transcript
   loss and self-report gaming — it is the only option that reduces false
   accepts and false rejects simultaneously, which is why this is the primary
   fix rather than loosening the transcript check itself.
2. **Reclassify empty-transcript rejections.** In
   `_verify_atomic_evidence_against_runtime_messages`, give the fully-empty
   `support_messages` case its own reason code (e.g.
   `transcript_missing_infrastructure`, reusing the existing
   `*_transient_exhausted` code convention) instead of a generic worker
   rejection. Route that code to a narrower retry: re-collect the transcript
   once, not re-run the whole AC. The 19m34s of real, already-completed work
   in the observed incident should never be discarded outright — an empty
   transcript is a collection-failure signal, not a gaming signal (a gaming
   worker leaves plausible-looking messages, not none).
3. **Rejected alternative:** falling back to workspace diff/mtime as a
   substitute signal when `support_messages` is empty. Rejected because it's
   gameable (`touch` satisfies it) and undermines the reason fat-harness
   exists.

## Rollout

1. **Phase A ships first, standalone PR.** Self-contained to
   `_run_ac_verify_gate` + new `verify_shell.py`; POSIX behavior is
   equivalent to today (`bash -c command` vs shell-default), so regression
   risk is low and fully unit-testable by monkeypatching `os.name`,
   `os.environ`, `shutil.which`, `Path.exists` — Windows branches are
   covered without Windows CI.
2. **Phase B3 (reclassification) ships next.** Pure improvement, harmless to
   existing seeds.
3. **Phase B1 (preflight gate) ships last, in two stages.** Release N: warn
   only (surfaced in preflight output, does not block). Release N+1: hard
   block, once telemetry shows the violation rate on existing seeds is
   acceptable. Escape hatch is a config flag
   (`seed.verify_command_gate: warn|block`, defaulting toward `block` over
   time) — no permanent opt-out. In-flight/resumed sessions are exempt from
   re-evaluation under the new gate so running workflows don't break
   mid-flight.

## Explicitly out of scope

- Native PowerShell/cmd `verify_command` authoring support — the contract
  stays "POSIX bash", with Tier 2 translation as the only accommodation.
- Automatic Git Bash / WSL installation.
- Retroactive migration of existing seeds to add `verify_command`.
- Redesigning the fat-harness evidence model itself beyond the empty-
  transcript reclassification.
- Changing verify_command's sandboxing/permission model.

## Implementation status

Shipped:

- **Part A, Tier 0 + terminal case.** `src/ouroboros/orchestrator/verify_shell.py`
  resolves a real bash (env `OUROBOROS_VERIFY_BASH` -> config
  `orchestrator.verify_bash_path` -> `/bin/bash`, `/usr/bin/bash`, PATH `bash`;
  Windows: Git Bash under `%ProgramFiles%`/`%ProgramW6432%`/`%ProgramFiles(x86)%`
  -> PATH `bash.exe`). `_run_ac_verify_gate` now runs
  `create_subprocess_exec(shell, "-c", command)` instead of
  `create_subprocess_shell`. There is **no `sh` fallback**: `sh` reads the same
  text differently (`echo -e X` prints `X` under bash and `-e X` under `sh`),
  so a contract asserting on `-e` fails under the shell it was written for and
  passes under the substitute — a verdict about a different command. A machine
  without Bash records verification as unavailable; it never emulates Bash and
  never converts the missing verifier into a worker failure. Windows never falls back
  to `cmd`, and never to `%SystemRoot%\System32\bash.exe` (the WSL launcher,
  whose filesystem the gate's `cwd` does not name). Only absolute resolved
  paths are accepted, because the gate launches with `cwd` set to the
  verification workspace and a relative path would name a different binary
  there than the one that was checked. `OUROBOROS_VERIFY_BASH` is on the
  untrusted-`.env` denylist, together with the shell startup and option
  controls (`BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `BASH_FUNC_*`), which
  the gate also strips from its own child environment: bash sources `BASH_ENV`
  before evaluating a `-c` command, so a repo-supplied file containing
  `exit 0` would otherwise turn any failing contract into a pass. Resolution is
  memoized per (OS, override, config, PATH, Windows install roots).

  Correction to the Decision section above: POSIX behavior is **not**
  equivalent to before. `create_subprocess_shell` runs `/bin/sh -c`, so verify
  commands previously ran under `sh` — `dash` on Debian/Ubuntu. They now run
  under `bash`, or not at all. Two directions of change, both intended: a
  bashism that used to fail the gate now runs as authored, and a machine with
  no Bash now reports verification unavailable; it never records a worker
  failure or consumes a worker retry. The sealed resolved Bash identity is
  selected once for the execution and revalidated by canonical path plus file
  digest before a pending verifier subprocess starts. A changed or missing
  identity remains unavailable rather than silently selecting a new executable.
- **Part A, unavailable outcome.** `verify_quarantine.py` preserves a successful
  worker result and emits an operator-visible unverified-success event. Startup
  errors and timeouts use the same path. The final settlement revalidates
  artifacts and workspace state but never turns unavailable verification into a
  worker failure.

  `BLOCKED` and retryable failure classes remain reserved for worker/runtime
  failures. Verifier infrastructure is a separate fact and does not enter
  route escalation or worker redispatch.
- **Part B3, transcript unavailability.** A fully empty `support_messages`
  projection yields `VerifierStatus.UNAVAILABLE` with
  `TRANSCRIPT_MISSING_INFRASTRUCTURE` and `ACCEPT` admission. Completed work is
  retained as unverified success; no worker retry or redispatch occurs.
- **Part B1, warn stage.** `AcceptanceCriterionSpec.verify_exemption_reason`
  (authored as the optional `exempt` key), `core/seed_verify_gate.py`, and
  config `seed.verify_command_gate` (`warn` default, `block` available) run at
  new-session preparation. The exemption is mutually exclusive with a command
  and survives acceptance normalization and semantic identity transfer.

Deferred, with the reason:

- **Tier 1 / Tier 2 (LLM route selection and translation) and the on-disk
  machine cache.** Tier 0 plus quarantine already avoids both dead-ending and
  faking a pass. The caches in the Decision section exist to amortize LLM
  calls; with no LLM tier wired, an on-disk cache for a four-syscall lookup
  would only add a staleness hazard. `resolve_verify_shell()` returning `None`
  is the seam these tiers would attach to.
- **Durable transcript re-collection.** There is no durable full per-AC tool
  transcript to replay yet. Event-native acceptance contracts and trajectory
  sealing are tracked separately; until then, missing transcript evidence stays
  explicit `UNAVAILABLE` and never causes repeated provider work.
- **B1's `block` default.** Shipped as `warn` per the staged rollout; flipping
  the default is Release N+1, after telemetry on existing seeds.

Incidental extractions required by the `#1797` module-size ratchet (the two
touched modules could not grow): `orchestrator/verify_gate_outcome.py` (gate
outcome type, checkpoint encoding, `expected_artifacts` oracle) and
`bigbang/acceptance_criteria_parsing.py` (strict AC JSON boundary).

## Follow-on finding: a verify_command that cannot fail

Everything above concerns *delivering* the gate's judgment faithfully on any
machine. It never asked whether the judgment has content. Measured on the tree:

```
verify_command='exit 0'        -> gate passed = True
verify_command='true'          -> gate passed = True
verify_command='printf READY'  -> gate passed = True

required evidence without verify_command: files_touched, commands_run, tests_passed
required evidence with    verify_command: files_touched
```

The follow-on implementation uses a monotonic evidence rule instead of a
constant-verdict proof. A verify command adds deterministic evidence but never
removes `files_touched`, `commands_run`, or `tests_passed` obligations and never
recovers a failed worker result. Therefore `exit 0` cannot weaken acceptance,
and no general shell-status interpreter is required.

When no real Bash resolves, or command startup/timeout prevents judgment, the
gate records an unavailable outcome. Successful work remains successful and is
reported as requiring confirmation; no provider retry or redispatch occurs.
