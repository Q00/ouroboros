# Troubleshoot Ouroboros with an AI assistant

Use this guide when installation, an MCP connection, an execution, or an update does not behave as expected. Identify the affected environment, inspect the symptom, preserve existing work, choose a targeted action, and verify the outcome. A host plugin can work without a standalone `ouroboros` command in your shell.

**Version boundary:** This guide describes source revision [`592c667f076c3dad7ef68d7844e91480d80135d0`](https://github.com/Q00/ouroboros/tree/592c667f076c3dad7ef68d7844e91480d80135d0), checked on 2026-11-07. A published package, a host plugin, and the MCP server launched by that host can be different versions. Check the help and behavior of the installation involved before applying these instructions. Source review and package inclusion do not establish that every host, authentication method, model, or recovery path has been tested.

## Start here

Tell the assistant which machine and operating system, host application, project directory, command or request, symptom, and last error are involved. Preserve the actual job, session, execution, and auto-session IDs, if any. Ask the assistant to distinguish observations from inferences, and commands it actually ran from commands it recommends.

If the affected environment has a standalone CLI, run these in its shell:

```bash
command -v ouroboros
ouroboros --version
ouroboros --help
```

In PowerShell, use `Get-Command ouroboros` to locate the command. The result identifies that shell's CLI, not necessarily the MCP server launched by a host. If the command is missing, check the host's own plugin and MCP status; do not install another CLI solely to infer the host server's version. A different machine, user, home directory, virtual environment, or host session can select a different installation. For a source checkout, `git rev-parse HEAD` identifies that checkout, not a separately installed package.

**Review output before sharing it.** Paths, project names, prompts, IDs, configuration errors, and launcher arguments can contain private information or secrets. Redact them as appropriate. Do not send credentials, tokens, a complete environment dump, or an entire configuration file. In particular, `doctor install` can display configured launcher arguments.

## Choose the symptom

| Symptom | First step | If that does not resolve it |
| --- | --- | --- |
| The shell cannot find `ouroboros`, or the host does not recognize `ooo` | Separate the standalone CLI from the host plugin; check the affected session and installed version. | Inspect the host's plugin status and installation instructions for that version. Do not assume one installation proves the other. |
| MCP tools are unavailable or connection fails | Check whether the host reports its server enabled and connected; preserve the redacted error. | Follow **MCP connection** below. |
| Authentication fails or health reports a credential warning | Identify the selected backend and the environment that actually launches it. Check its supported login or credential setup without sharing the credential. | A credential-presence check does not prove validity; verify an authorized connection separately. |
| A job appears stuck or a client disconnected | Preserve the original IDs, workspace and owner; query the existing work. | Follow **Status and recovery** below before retrying. |
| Codex uses broader file or network access than expected | Check the existing job, actual worker command, and product/Codex versions. | Follow **Permission and isolation scope** below. |
| An update reports partial failure | Identify which package and refresh step changed. | Follow **Update and partial failure** below. |
| A job completed but the result seems wrong | Compare the Seed and actual files, tests and evaluation evidence. | Follow **Verify and report** below. |

## Diagnose without assuming a pass proves success

Run the following in the affected CLI environment only if that installation provides them. Consult the relevant `--help` first and inspect the individual errors and warnings, not just the exit code. These checks are diagnostic, not repair commands; nevertheless, logging, initialization, and dependency imports can create local traces or make network requests. They are not a promise of offline or OS-isolated operation.

| Command | What it inspects | What a pass does not establish |
| --- | --- | --- |
| `ouroboros doctor install` | Package, plugin and MCP installation surfaces and launcher information. | A live host connection or successful task. |
| `ouroboros status health` | Configuration, database path, runtime availability and credential presence. | Valid authentication, a model call, or successful execution. |
| `ouroboros mcp doctor` | MCP prerequisites; the default does not start a server. | The actual host connection or a model call. |
| `ouroboros mcp doctor-runtime` | Bounded executable provenance, ephemeral loopback bindability and Ouroboros server registry metadata. | A live connection between the host and server. |
| `ouroboros codex doctor` | Codex `ooo auto` dispatch artifacts and MCP configuration. | A live host connection or model call. |

`doctor install`, `mcp doctor`, and `mcp doctor-runtime` support `--json` in the source revision above. For `mcp doctor`, `--machine-snapshot --json` returns an object containing `checks` and `machine_snapshot` rather than the default list. Redact either form before sharing. A configuration error in `status health` remains important even if other rows report `ok`. See the [installation doctor](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/doctor.py), [MCP doctor](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/mcp_doctor.py), and [health implementation](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/status.py).

## MCP connection or authentication fails

1. In the original host session, check whether the plugin and Ouroboros server are enabled and whether the error concerns server startup, connection, tool discovery, or authentication. Inspect the server's command or URL and environment without exposing secrets. A CLI health pass does not prove that this host uses that CLI or server.
2. If the relevant standalone CLI is available, read the failing rows of `ouroboros mcp doctor`. For Codex, `ouroboros codex doctor` checks the `ooo auto` dispatch setup. A failure gives a starting point; inspect the suggested changes and target before applying them. A pass still does not prove the host connection.
3. If an additional process is appropriate, `ouroboros mcp doctor --probe-local-stdio` starts a temporary local child and checks startup and tool discovery without invoking a tool. It does not test the host's configured launcher, authentication, or model. Its Python-level restrictions are not OS confinement; interpreter startup can precede them. Ordinary doctor checks may also attempt network access.
4. `ouroboros codex doctor --live-mcp` instead launches the **configured stdio server** and checks discovery. Inspect that launcher and its potential network and other effects first. This option does not verify a URL transport or a model call. See the [Codex doctor implementation](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/codex.py).
5. If setup reports `No runtimes found.`, inspect the runtime executable, configuration and help in the setup process's environment. Detection can involve more than the current shell's PATH. Setup and refresh can change configuration and artifacts; a failed setup does not prove that no local state was created. Preserve existing files and inspect the failed step before retrying. See [setup](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/setup.py).
6. In the Python `MCPClientAdapter` path, an SDK exception whose text contains `not found` can be misclassified as a missing tool. One comparison using the candidate offline dev server and an independent MCP SDK call checked a registered `ouroboros_job_result` with a synthetic nonexistent job ID: `Job handle not found` surfaced from the adapter as `Tool not found: ouroboros_job_result`. This is one observed Python-adapter path, not a rule for every host or SDK. Before classifying this message, confirm the same host is connected to the intended server, inspect that server's actual registered tool list, and compare the exact job ID with the original start response. Preserve the original structured error and relevant versions, but do not share secrets, full environment/configuration, or sensitive payloads. See the `MCPClientAdapter` exception handling in [main](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/client/adapter.py#L408-L412) and [release `v0.59.9`](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/client/adapter.py#L408-L412).

**Native Windows Codex Desktop exception:** In both the cited main source and release `v0.59.9`, setup's `auto` mode can preserve an existing MCP entry, or skip a new persistent entry, while returning success. Inspect the actual Ouroboros entry and the host's current tool list; setup's success alone proves neither registration nor connection. Review only the relevant config entry and redact paths or arguments before sharing. For the separate loopback HTTP mode, first check the installed `ouroboros setup --help` and the exact target. Only within the user's approved configuration change, run `ouroboros setup --runtime codex --mcp-mode http`; it prints a server command that must be started separately before opening Codex and registers `http://127.0.0.1:8765/mcp`. If using stdio on Windows, use the Codex CLI in WSL 2 and check that WSL environment. See [Windows behavior at main](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/windows_codex_mcp.py) and [release `v0.59.9`](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/cli/windows_codex_mcp.py).

After an authorized correction, repeat the relevant check in the same host and environment. If a real connection or model call was not tested, report that limit.

## Codex permission and isolation scope differs from expectations {#permission-scope}

1. Start in the original host conversation: identify the `job_id`, `session_id`, `execution_id`, owner, and current state. Follow [Status and recovery](#recovery) to query that same job and its result. Do not start a duplicate or terminate a user-owned session just because a response disappeared.
2. Inspect the actual worker command and selected backend/runtime for that job. Codex `--sandbox workspace-write` allows writes in the workspace while retaining a sandbox; `--dangerously-bypass-approvals-and-sandbox` bypasses both Codex approvals and its sandbox. Do not infer effective permissions from a setting name alone, and do not dump tokens or complete environment/config files.
3. Permission can vary by path. When no permission mode is supplied to `CodexCliRuntime` itself, its default is `acceptEdits`, mapped to `workspace-write`. That default does not describe every internal call. With no explicit permission, the `use_case="interview"` Codex factory may select bypass for question generation. The `OrchestratorRunner` can overwrite the adapter permission mode passed to it with `bypassPermissions`; eligible cross-harness retries and a specific pytest collection-error repair path also set bypass separately. Do not assume a single Codex setting constrains nested runs and retries. These paths were checked in product main `592c667` and release **0.59.9**.
4. Check the host OS isolation actually applied: process namespaces, visible files and writable paths, and network egress. If a Codex sandbox-bypass flag appears, do not treat Codex configuration alone as proof of OS isolation.
5. If the job owner or live process is unknown, preserve its files, branch and external effects; do not terminate a user session or change authentication/configuration. Before stopping or cancelling, identify the exact job and owner process and check effects already made.
6. `model_tier=small` requests a starting tier; it does not guarantee that tier or cap cost, tokens, or model request count. Whether it takes effect and which model runs can depend on an explicit model pin, router activation conditions, and the runtime’s native model-override support. Separate role calls may also occur. Retries or tier escalation may create additional sessions or use a higher tier. Check available per-job/session model, token, and cost records. If usage evidence is unavailable, report it as unknown and do not repeat the run just to measure it.

## Status and recovery after a disconnect

A closed client or missing response does not establish that a worker stopped. Find the original host conversation, start tool, and returned field names first; distinguish `job_id`, `session_id`, `execution_id`, and `auto_session_id`. A field named `session_id` does not by itself mean an execution session. An Interview MCP start response uses `state.interview_id` as its `session_id`; that is a different ID from an orchestrator execution session. Do not pass it to the execution-session commands below. `ouroboros status run --session-id` accepts orchestrator session IDs only. The MCP tool `ouroboros_session_status` queries orchestrator sessions and also handles `auto_<id>` IDs by returning auto-session status; an Interview ID is a separate type. See [main Interview start response](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/authoring_handlers.py#L2661-L2713), [main status query scope](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/query_handlers.py#L291-L323), [main session reconstruction requirement](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/orchestrator/session.py#L1298-L1342), and [CLI run status option](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/status.py#L374-L389). The same behavior was checked in release `v0.59.9`: [Interview response](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/authoring_handlers.py#L2686-L2738), [status query](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/query_handlers.py#L291-L323), [reconstruction requirement](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/orchestrator/session.py#L1298-L1342), and [CLI option](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/cli/commands/status.py#L374-L389). For standalone CLI status checks, replace each placeholder below with the **matching ID of the indicated type**, and check the installed help first:

```bash
ouroboros job status JOB_ID
ouroboros job result JOB_ID
ouroboros status execution EXECUTION_ID --events
ouroboros status run --session-id ORCHESTRATOR_SESSION_ID
ouroboros status auto AUTO_SESSION_ID
ouroboros resume --list
ouroboros resume --all --list
```

### Resume an interview

To continue an Interview, use the same `session_id` with `ouroboros_interview` in the original host/MCP and send the user's actual answer as `answer`. This is a continuation, not a status-only query; it can generate another question and incur model calls and cost. For a standalone CLI interview, use the **same state directory as before** with `ouroboros init list` to find its ID, then `ouroboros init start --resume INTERVIEW_ID` to continue it. If you used `--state-dir`, pass that same path to both commands. `ouroboros resume --list` lists execution sessions, not interviews. If the host returned `delegated_to_subagent`, use the actual ID shown in the original host's Task pane; the delegation receipt is not the interview ID. See [main Interview continuation](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/authoring_handlers.py#L2280-L2305), [main CLI interview resume option](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/init.py#L1028-L1034), and [CLI list/state directory](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/init.py#L1212-L1246). The same behavior was checked in release `v0.59.9`: [Interview continuation](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/authoring_handlers.py#L2263-L2324) and [CLI resume/list](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/cli/commands/init.py#L1028-L1034).


**Interview calibration depends on the server version.** The fixed main source `592c667f` recognizes a non-empty `calibration_input` as a calibration action before ordinary start, answer, or resume dispatch. Release `v0.59.9` does not expose that field in its Interview schema or handle it as calibration: if an unsupported argument nevertheless reaches the handler without `initial_context`, it selects an answer when `answer` is present and otherwise a resume, which requires `session_id`; a host or schema may reject the argument earlier. Do not send `calibration_input` or `interview_calibration` to that release or assume it was processed; an answer or resume can change interview state and invoke a model. Check the actual connected server's tool schema and version, preserve the pending question, and use only the input that server supports; ask for an explanation in the existing host conversation instead. See [main action selection](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/authoring_handlers.py#L2100-L2128), [main calibration parameters](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/interview_calibration.py#L22-L42), and [release action selection](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/authoring_handlers.py#L2093-L2123). Other installed versions or host schemas require separate checking.

`ouroboros init start --resume INTERVIEW_ID` is not a read-only status command. It continues the interview, can call the selected model for questions or scoring (and incur cost), and can update saved interview state. Depending on the path, `Proceed to generate Seed specification?` defaults to `yes`; generating a Seed writes an artifact. After Seed generation, `Start workflow now?` also defaults to `yes`, so accepting the default (pressing Enter) can start actual workflow execution. To inspect the Seed before execution, enter `n` at `Start workflow now?`; if you do not want a Seed generated, enter `n` at the Seed prompt. See [main interview, Seed, and workflow flow](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/init.py#L560-L654), [main Seed persistence and workflow handoff](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/init.py#L748-L812), [release flow](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/cli/commands/init.py#L559-L653), and [release Seed persistence and workflow handoff](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/cli/commands/init.py#L748-L812).

### Inspect jobs and execution sessions

`job result` reads the terminal output for the same job ID, including a `failed`, `cancelled`, or `interrupted` job; it is not limited to successful work. Read its status/error fields and returned failure text or payload as evidence about the outcome. A successful query only means the record was read; it does not mean the work passed its criteria. In the cited main source, `worker_blocked` is a closed failure category derived from a worker judgement class. It does not identify the underlying reason by itself. Inspect the actual result, any linked session or execution ID, and the worker's relevant output before attributing the cause. If available through the owning host, inspect only the relevant stdout/stderr and permission, backend/runtime, and environment error details; redact tokens, keys, credentials, and unrelated environment values before sharing. The source does not guarantee that raw stdout/stderr is persisted in the job result. Preserve the existing workspace, branch, uncommitted files, and external effects; do not rerun, resume, cancel, or start a duplicate while the owner or current state is uncertain. `resume --list` lists execution-session candidates; it is not an Interview list and does not resume them. A list can be limited or omit sessions whose records could not be reconstructed, so an empty list is not proof that no work exists. A database open error is not an empty history. See [job result and status semantics](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/job_handlers.py), [worker failure categories](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/orchestrator/run_failure_cause.py), [status](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/status.py), and [resume listing](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/resume.py). The cited source is main at `592c667`; installed releases and host integrations may differ.


**A pending detached start is not proof of a failed or completed job.** If the original start returned `detached_job_acceptance_pending`, preserve that receipt and its exact `job_id`. In main `592c667f`, when the normal snapshot lookup cannot find a job but a matching pending receipt is known, `ouroboros_job_result` can return non-terminal `acceptance_pending` with worker state unknown. In release `v0.59.9`, the same missing durable lookup can instead return `job_handle_not_found` with `lifecycle_status: invalid` and `is_terminal: true`; those fields describe the lookup response and do not prove the worker stopped or that it is safe to restart. Check the original receipt and ID, the connected server and its version, and the owning process or host; inspect the same job through the supported status path. If acceptance or ownership remains uncertain, preserve the records and workspace and do not start a duplicate. See [main pending-result branch](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/job_handlers.py#L2065-L2089), [main pending response](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/job_read_state.py#L124-L154), and [release missing-handle response](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/job_handlers.py#L2064-L2084). The pending receipt must be available to the main read path; this does not guarantee one exists or that every missing handle is pending.

For a wider execution-session candidate list, `ouroboros resume --all --list` removes the normal snapshot path's 20-row cap. It still lists only sessions reconstructed as `running` or `paused`; reconstruction failures are omitted. An older EventStore fallback replays session events without applying that cap, so `--all` may not add rows there. Neither form proves that a worker process is still alive, reveals all historical sessions, or resumes work. Check the installed help and keep using the original IDs to inspect known work. These details were checked in both the cited main source and release `v0.59.9`: [main resume implementation](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/resume.py) · [release `v0.59.9`](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/cli/commands/resume.py).

Before resuming, cancelling, or starting a new run, establish the original owner and terminal state, Seed **file path**, target workspace and branch, uncommitted files, and effects already sent to external systems. Do not start a duplicate because a receipt was lost. In the cited revision, a particular `run workflow --resume` failure caused by an unavailable process-local check package can record the original session as failed and start a new attempt. Inspect the installed behavior and target before choosing a recovery action. Cancellation does not undo completed external effects. See [run recovery](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/run.py).


**Check separately chained jobs before treating a stop as complete.** In the fixed main and release sources, a run can enqueue a separate evaluation job named by `chained_evaluate_job_id`; its evaluation result can in turn name a separate Ralph job in `chained_ralph_job_id`. These fields appear only when the corresponding chaining path succeeds; do not assume every run has them. Cancelling the original job or execution does not automatically establish that a separately chained job was cancelled, especially after the original is terminal. Inspect the original result, then the evaluation result if present, and check each returned job ID's status and result with the same server. If the user explicitly requests that a still-running follow-up stop, identify its exact ID and owner and request cancellation for that job separately using the installed server's `ouroboros_cancel_job` schema. Check its later status and result, and verify external effects; a cancellation request is not proof of termination or reversal. Preserve existing files and do not guess at missing IDs or start replacement work while the state is uncertain. See [main evaluation receipt](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/run_evaluate_chain.py#L150-L175), [main Ralph receipt](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/evaluate_ralph_chain.py#L462-L472), [main job cancellation](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/job_handlers.py#L2148-L2189), and the corresponding release [evaluation](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/run_evaluate_chain.py#L150-L175) and [Ralph](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/evaluate_ralph_chain.py#L462-L472) paths. Other versions and host integrations may differ.

If the owner, state, target, or external effects remain unknown, preserve the records and ask the person responsible before guessing or starting another attempt.

## Update and partial failure

`ouroboros update --check` queries remote release information; it is not an offline check. Before updating, identify the package manager and executable, affected hosts and running work. An update or refresh may change installed files and settings.

If output says `Ouroboros partially updated`, the package may already have changed even though a later refresh failed. Check `ouroboros --version` in the same environment, preserve the error, and identify the failed step. Review the suggested recovery command and its target before running it. In the cited revision, rerunning `ouroboros update` when the package is already current does not automatically retry failed runtime refreshes. Do not delete or overwrite existing configuration merely to silence an error. See the [update implementation](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/update.py).

## Verify and report

After a targeted, authorized change, repeat the original check in the same machine, host and installation. For a task result, compare the Seed's goal and acceptance criteria with the actual changed files, test and evaluation output, and unresolved failures. A job ID, health `ok`, terminal job state, successful query, or evaluation request alone does not prove the requested result was achieved.

Report the redacted symptom, identified installation and version, relevant ID types, commands actually run and their results, changes, and remaining uncertainty. State explicitly if real host connection, authentication, model use, external effects, or recovery were not tested. Do not claim that an action succeeded solely because it was suggested.
